 retries on 429/5xx/network errors. Regression tests cover the scope split, throttling independence and rotation reuse-rejection.
- **Android: "Save & reload" on the server-address field did nothing** — the ServerField `<form>` was nested inside the login `<form>`. Submit events never cross a form boundary while bubbling (the outer form's submission behavior stops propagation), so React's root-delegated `onSubmit` on the inner form never fired: the address was never stored, the page never reloaded, and every login attempt then went to a server that was never set (reproduced in headless Chromium: save handler 0 calls, localStorage empty). Never noticed before because the per-deployment APK (baked `MAIN_HOST`) never requires saving. ServerField now renders as a sibling of the login form - click *and* Enter both save reliably.
- **`apk` CI job: Capacitor CLI requires Node >= 22** — the job pinned Node 20, so `npx cap sync android` died with "The Capacitor CLI requires NodeJS >=22.0.0" after the web build had already succeeded; no release APK has been attached by CI since the Capacitor 8 upgrade. The job now sets up Node 22.
- **Android: profile pictures STILL missing + forced login on every app reopen** — two follow-ups to the avatar/session work: (1) the native avatar loader passed `CapacitorHttp`'s blob response straight to `FileReader.readAsDataURL()`, but the Android bridge returns binary bodies as a **base64 string** (`HttpRequestHandler.readStreamAsBase64`), not a `Blob` - the call threw a TypeError, the catch swallowed it and every avatar silently fell back to the placeholder; the loader now builds the `data:` URL directly from the base64 payload + response Content-Type (whitespace-stripped - Android's `Base64.DEFAULT` wraps lines). (2) `apiRefreshToken()` (the login page's auto-login) stored only the new *access* token and dropped the *rotated refresh token* - with `ROTATE_REFRESH_TOKENS` + `BLACKLIST_AFTER_ROTATION` the just-used refresh token is dead the moment the response arrives, so localStorage kept a blacklisted token and the next refresh (minutes later) failed: every app reopen ended back at the credentials form. The rotated refresh token is now stored, and the Welcome page (the APK's cold-start URL) redirects straight to the dashboard when a refresh token exists - an expired one still bounces to /login via the normal reauth path.
- **In-app update banner never appeared in the Android app** — the check fetches `/download/apk-version.json` from the WebView (origin `https://localhost`), but nginx's `/download/` location sent no `Access-Control-Allow-Origin`, so the WebView hid the response and the check died silently in its catch. The location now answers with `Access-Control-Allow-Origin: *` (public, unauthenticated files).
- **Android: "OWHealth plugin is not implemented" + missing avatars** — the custom OWHealth plugin was registered *after* `super.onCreate()`, but `BridgeActivity.onCreate` builds the Bridge and consumes the plugin list in that call, so the plugin never existed; it is now registered before (Capacitor's documented order). Profile/persona pictures failed silently in the WebView: the authenticated loader now uses `CapacitorHttp` (native OkHttp - no WebView CORS/blob quirks) and renders via `data:` URLs (`safeImageSrc` allows `data:image/`).
- **Health Connect linking in the Android app died with "Failed to fetch"** — the app redeems the invitation code from its Capacitor WebView (origin `https://localhost`), but the bundled Open Wearables defaults `CORS_ORIGINS` to *empty*, so its CORSMiddleware never emitted `Access-Control-Allow-Origin` and the WebView blocked every response (preflight and POST both). The `openwearables` service now sets a default CORS allowance for the app origin (`OW_CORS_ORIGINS` knob) — **as a JSON list** (`["https://localhost"]`), because pydantic-settings JSON-decodes list-typed env vars and a bare string makes OW crash at startup (verified against the pinned image).
- **The `apk` CI job never shipped an APK** — every release so far carries only `docker-compose.yml` + `.env.example`: GitHub Actions sets `CI=true`, which makes the CRA build inside the apk job treat the (tolerated) ESLint warnings as fatal errors, so "Build web bundle" died before Gradle ever ran. The step now builds with `CI=false`, matching local builds - reproduced and verified. The upload step had a second latent bug: `gh release upload file.apk#workout-challenge.apk` sets the asset *label*, not its name, so the release would have shipped `app-release.apk`, which `update_apk_from_release.sh` never finds - the step now renames the file before upload. Release `0.11.0` was back-filled manually (locally built APK, correctly stamped 0.11.0/101).
- **`update_apk_from_release.sh` no longer needs the gh CLI** — it now uses plain curl + python3 (no interactive `gh auth login` on the server, so it is actually cron-friendly on a fresh VPS), auto-detects the GitHub repo from the running image's `org.opencontainers.image.source` label (git remote / `REPO_SLUG` as fallback), works on public repos without any token (`GITHUB_TOKEN` only for private forks), and fails with a clear "release X has no APK attached - did the apk CI job succeed?" message instead of gh's opaque pattern error.

### Security
- **Dependabot alert 110 (`postcss`, CVE-2026-69153) resolved** — the flagged instance is `postcss@7.0.39`, nested under `resolve-url-loader` in the react-scripts 5 build chain; no resolve-url-loader release supports postcss 8, so it is structurally not upgradable (forcing it would break the CSS build). The vulnerable code path - processing attacker-controlled CSS with a malicious `sourceMappingURL` - is never exercised: the loader only rewrites our own checked-in CSS at image build time. The first-party postcss (root devDependency) floor is now pinned at `^8.5.23` (lock already resolved 8.5.25, i.e. patched) so it can never regress into the vulnerable range, and the alert is dismissed on GitHub as tolerable risk with this justification.
- **CodeQL `js/xss-through-dom` on the persona avatar** — the pre-upload preview in the persona editor passes a DOM-derived object URL through the persona payload into `<img src>`. Practically unexploitable (browser-minted `blob:` URLs can't execute script in an image), but the sinks are now whitelist-guarded: only `blob:` and same-origin relative URLs may reach `<img src>` (`safeImageSrc()` in `PersonaAvatar.js`), and - the genuinely valuable part - the JWT-carrying image fetch in `protectedMedia.js` now only requests same-origin relative paths, so a malicious API payload can never point the authenticated fetch at an attacker host to exfiltrate the token.
- **All uploaded pictures are no longer public** — uploaded images (Drill Instructor persona pictures *and* user profile pictures) must never be reachable without a login (search engines, hotlinks, scraped `/media/` trees; persona artwork may additionally be copyrighted material). Each file is now served only through an authenticated endpoint - `GET /api/drill-instructor/persona/<id>/picture/` (any logged-in user) and `GET /api/user/<id>/picture/` (the owner or a co-participant; `/api/user/me/picture/` works too): Django checks the JWT and hands delivery to nginx via `X-Accel-Redirect` from a non-public `internal` location (`/protected-media/`). The whole `/media/` tree now answers 404 from the outside. Responses carry `X-Robots-Tag: noindex, nofollow` and `Cache-Control: private, no-cache` (the URLs are stable per user/persona, so browsers revalidate via ETag and see an uploaded replacement immediately, while shared caches never store the bytes). The API payloads (user, persona, drill-message, leaderboard stats) expose only these endpoint URLs (uploads moved to write-only `profile_picture_upload` fields), and the frontend renders the images from object URLs fetched with the JWT (`blob:` added to the CSP `img-src`).
