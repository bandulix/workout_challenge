date` (500-row batches), an id snapshot so mid-run requests survive, and one `in_bulk` goal fetch for all groups.
- **Scorer bulk paths batch their writes** — new workout / new goal / competition date changes / user joins / scaling-factor and sport-factor re-scores all wrote per-row INSERTs and re-read the sport factors per row; they now use `bulk_create`/`bulk_update`, hoisted factor maps, and `select_related`/`prefetch_related` (a 500-workout user joining a 3-goal challenge went from ~1500 sequential INSERTs to a handful of round trips). A start_date shortening only enqueues recalcs for (user, goal) pairs that actually lost points (was the full cartesian product).
- **Hourly syncs no longer churn caches for nothing** — re-saving an unchanged activity early-returns before the stats-cache bust + recalc enqueue (previously every known activity, per user, per hour, invalidated every challenge snapshot it touched). Garmin/Health syncs load only the fetched page's ids instead of the whole table's provider rows; Strava's redundant whole-table id set is gone (the per-page map already covers it, including the cross-account takeover guard).
- **Activity feed endpoint is cached per stats generation (30s TTL)** — it rescanned the competition's entire Points table twice per request, uncached, on every 60-90s poll; it now shares the stats generation key (permission check still runs first on every request).
- **Settings resolution cached for 60s** — Strava rate-limit checks, LLM config and OW connector config each hit the SiteSettings row on every call; now cached briefly and invalidated on save, so admin edits still apply without restart.
- **Stats tail: one query less** — owner `select_related` and `len(members)` instead of a second COUNT query.
- **Weekly/leaderboard emails: one task per user** — the scheduler joins produced one row per active competition, so users in N challenges got N duplicate emails; both queries now use `distinct()`.

### Fixed
- **Activity-goal edits now refresh the challenge page right away** — the goal form only invalidated its own cache namespace, but the page reads stats + feed, so edited/deleted/new goals lingered until the 90s poll (and the alert text claimed "up to 10 minutes"). The factors shown in the info view are also refetched on every open (were cached up to 12h after an admin edit).
- **Migration drift in drill_instructor resolved without touching the DB** — `0012` added the one-comment-per-workout unique constraint as a deliberately DB-only guard (its IntegrityError is what suppresses double coach comments under concurrent tasks), but as a plain `AddConstraint` it also entered the migration *state*, so `makemigrations --check` permanently wanted to drop a protection the code relies on. `0013` is a `SeparateDatabaseAndState` state-only removal: the model state is clean again and the database keeps enforcing the guard (verified: sqlmigrate is a no-op).
- **Goal equalizer forgot your inputs on every open** — the modal only ever loaded the profile gender and otherwise fell back to the hardcoded defaults (35y/180cm/75kg), because the raw inputs are intentionally never sent to the server ("stay on your device") - but they were never stored on the device either. They now persist in localStorage (`wc_equalizer_inputs`) and are pre-filled on reopen; still only the two derived percent factors ever leave the device.
- **Garmin: daily step totals were imported as workouts** — some devices/loggers push all-day step summaries into the Garmin activity list; the sync mapped them to a generic "Workout" row. Step-type records (`steps`/`daily_steps`/`all_day_steps`/`step_tracking` typeKeys - exact matches only, so real stair-stepper workouts keep importing) are now skipped, and a row imported by an earlier version is deleted again on the next sync (per-object delete, so points recalc fires). Covered by two new tests (skip + cleanup, stepper still imports).
- **Health Connect "host not found" in the Android app** — the connection code handed phones the LAN/internal Open Wearables address (`HEALTH_PUBLIC_URL`, e.g. `http://<server-ip>:8001`): unreachable on mobile data and mixed-content-blocked under the HTTPS app on Wi-Fi. The container nginx now serves the OW API under the app's own domain at `/health/` (variable `proxy_pass` + docker resolver, so nginx boots fine when the health profile is off; verified end-to-end against a live stack), and `HEALTH_PUBLIC_URL` defaults to `MAIN_HOST/health` instead of the internal hostname - no reverse-proxy rule or LAN exposure needed any more (`OW_BIND` can go back to loopback). The app also names the cause when the health server can't be reached instead of surfacing a raw fetch error.
- **Android app updates rejected ("app not installed"), forcing uninstall + reinstall** — the `apk` CI job had no signing material, so `app/build.gradle` silently fell back to the debug key: every CI runner generated a fresh ephemeral debug keystore and **every release APK carried a different signature**. Android refuses in-place updates across signing identities (and the locally-built APK is release-key-signed, mismatching CI too), so no working update path existed. The CI now signs releases with the real release key when the `ANDROID_KEYSTORE_BASE64` / `ANDROID_KEYSTORE_PASSWORD` / `ANDROID_KEY_ALIAS` / `ANDROID_KEY_PASSWORD` secrets are configured (it materializes `~/.gradle/workout-signing.properties`, which `build.gradle` already auto-discovers); forks without the secrets keep the debug fallback. Note for existing installs: an APK signed by a CI debug key must be uninstalled once - afterwards every update installs in place, data kept.
